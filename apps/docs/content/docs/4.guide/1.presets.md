The SDK ships a large tool catalog so you can build almost any GitHub agent. **Presets** are how you keep that catalog out of the model's context: each preset exposes only the tools for one workflow. Start with the smallest preset that fits; use `maintainer` or omit `preset` when you need the full surface.

Tighten GitHub tool scope for this assistant using @github-tools/sdk.

- Switch to the smallest preset that still satisfies the feature; use an array to combine presets if needed (see https://github-tools.com/guide/presets)
- For multi-role products, prefer a manager agent with preset-scoped sub-agents (https://github-tools.com/examples/manager-agent-with-subagents)
- Align the GitHub PAT with https://github-tools.com/guide/tokens-and-auth

::

## Compose agents around presets

| Shape | When to use |
|---|---|
| **One preset** | A single job (review PRs, triage issues, cut releases) |
| **Array of presets** | One agent that spans a few related domains |
| **Manager + sub-agents** | Several distinct roles — each specialist mounts one preset ([example](/examples/manager-agent-with-subagents)) |
| **`maintainer` / omit preset** | Prototyping or a genuine need for the full catalog |

## Apply a single preset

Use a preset to restrict the tools to a specific capability domain. For example, a code review agent only needs pull request and commit tools:

```ts [review-agent.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools({
  preset: 'code-review',
})
```

Focused operator workflows:

```ts [security-audit-agent.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools({
  preset: 'security-audit',
})
```

```ts [pr-author-agent.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools({
  preset: 'pr-author',
})
```

## Combine multiple presets

When a workflow spans multiple domains, pass an array. This agent can both review PRs and manage issues:

```ts [triage-and-review.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools({
  preset: ['code-review', 'issue-triage'],
})
```

## Let the agent pick tools

When one agent handles open-ended requests, use `preset: 'auto'`:

```ts [auto-preset.ts]
import { createGithubAgent } from '@github-tools/sdk'

const agent = createGithubAgent({
  model: 'anthropic/claude-opus-5.5',
  preset: 'auto',
})

await agent.generate({ prompt: 'Why is CI failing on main?' })
// lists the core read tools plus the CI tools the request needs
```

A fast evaluation model reads the conversation's first request and rates how likely it is to need each tool. The agent lists the likely tools and the core read tools (`getRepository`, `getFileContent`, `getRepositoryTree`, `searchCode`, `listCommits`), usually 2k to 3k tokens of tool definitions instead of about 16k for the full catalog:

1. Tools rated at or above `minToolProbability` (`0.5`) are listed, most likely first, up to `maxTools` (`8`).
2. The core read tools are always listed, so a task never stalls on context.
3. When the evaluation call fails (model not enabled on AI Gateway, no credits, outage), the agent lists the read-only `repo-explorer` tools and logs a `github_tools.EVALUATION_FAILED` warning through `console.warn`.

The rest of the catalog stays reachable without changing the tool list. `createGithubAgent` adds a `callGithubTool` tool whose `name` names every GitHub tool: the model passes the tool's arguments as `input`, or omits `input` to get the tool's description and input schema first. The call goes through the named tool's approval, `toModelOutput` and overrides. The [eve extension](/frameworks/eve-extension#automatic-presets-and-approval) defers the rest instead, behind `eve__search`.

In approval requests and tool parts, these calls appear as `callGithubTool`, with the GitHub tool in `input.name` and its arguments in `input.input`. Read those when your UI shows which tool is about to run.

`preset: 'auto'` is available on `createGithubAgent` and needs `ai` 7.0.105 or later. To tune it, use `evaluation: { minToolProbability, maxTools, model }`. The default model is [Jev from TypeSafe AI](/guide/jev-typesafe-ai).

Outside `createGithubAgent`, call `selectTools` yourself and pass the result as `activeTools`. Call it once per conversation and reuse the result, so the tool list stays the same across requests:

```ts [pick-with-stream-text.ts]
import { createGithubTools, selectTools } from '@github-tools/sdk'
import { streamText } from 'ai'

const activeTools = await selectTools(messages)
const result = streamText({
  model: 'anthropic/claude-opus-5.5',
  tools: createGithubTools(),
  activeTools,
  messages,
})
```

### Keep the prompt cache across requests

Providers that cache prompts, such as Anthropic, cache from the start of the prompt: first the tool definitions, then the system prompt and the conversation. When the tool list changes between two requests, the provider can't reuse its cache and writes the whole conversation to it again, which costs more than reading it.

So `preset: 'auto'` picks the tools once, on the conversation's first request, and keeps them listed for the rest of it (`evaluation.scope: 'session'`, the default). A later request that needs other tools reaches them through `callGithubTool`, or `eve__search` in eve, neither of which changes the tool list. Set `scope: 'turn'` to pick tools again for each new request.

`createGithubAgent` keeps its decisions in memory, so on serverless another instance can decide again, which costs a decision call and can pick differently. Pass `evaluation.store` to keep them in your own storage. Keys are derived from the request the decision was made for, so the same first request gets the same tools across instances and conversations:

```ts [store.ts]
import { createGithubAgent } from '@github-tools/sdk'
import { kv } from './kv'

const agent = createGithubAgent({
  model: 'anthropic/claude-opus-5.5',
  preset: 'auto',
  evaluation: {
    store: {
      get: key => kv.get<string[]>(key),
      set: (key, value) => kv.set(key, value, { ex: 60 * 60 * 24 }),
    },
  },
})
```

The eve extension keeps decisions in the session already.

In the [eve benchmark](https://github.com/vercel-labs/github-tools/tree/main/examples/eve-bench) with Claude Opus 5.5, averaged over three runs, picking tools this way cost 27% less than listing the full catalog over six requests in one session, and about 10% less on single requests, where runs vary more. The same six requests sent to `createGithubAgent` cost 13% less than the full catalog.

### Route to presets instead

With `evaluation.selection: 'presets'`, the agent routes each request to presets and uses their system prompts:

```ts [auto-presets.ts]
import { createGithubAgent } from '@github-tools/sdk'

const agent = createGithubAgent({
  model: 'anthropic/claude-opus-5.5',
  preset: 'auto',
  evaluation: { selection: 'presets' },
})

await agent.generate({ prompt: 'Why is CI failing on main?' })
// runs with the ci-ops tools and system prompt
```

The evaluation model rates how likely the latest user message is to need each preset, and the agent exposes only the tools of the chosen presets:

1. Presets rated at or above `minPresetProbability` (`0.7`) are used, most likely first, up to `maxPresets` (`2`) per call.
2. The read-only `repo-explorer` preset is only used when no other preset qualifies, since every other preset already includes the core read tools.
3. When none reaches the threshold, or the evaluation call fails, read-only `repo-explorer` is used, so a vague request never gets write tools.

The agent routes once per request and reuses the result when the same request comes back, as in an approval continuation, so its tools don't change partway through a task. A short reply such as "yes" is routed together with the end of the assistant message it answers. The tools can change between requests, so a long conversation loses part of the provider's prompt cache: in the eve benchmark, preset routing cost 9% more than the full catalog on single requests, and more than twice as much when it routed each of six requests in one session. `createGithubAgent` can't route presets once per session, since it has no way to reach tools outside them; the eve extension does, because it defers the other tools.

Outside `createGithubAgent`, call `selectPresets` yourself and pass the result to `createGithubTools`:

```ts [route-with-stream-text.ts]
import { createGithubTools, selectPresets } from '@github-tools/sdk'
import { streamText } from 'ai'

const preset = await selectPresets(messages)
const result = streamText({
  model: 'anthropic/claude-opus-5.5',
  tools: createGithubTools({ preset }),
  messages,
})
```

The [TanStack AI integration](/frameworks/tanstack-ai) routes `preset: 'auto'` to presets, and doesn't support single tools yet. `selectPresets` is also exported from `@github-tools/sdk/tanstack`, where it takes the same `evaluation` options with `adapter` instead of `model`.

## Pick the right preset

| Preset | Tools included | Use case |
|---|---|---|
| `repo-explorer` | repository metadata, branches, file content, repo tree, code and issue search, discussions, gists, workflows, checks/statuses, releases | knowledge retrieval, repo Q&A |
| `ci-ops` | workflows, runs, jobs, job logs, checks/statuses, commits, repository context | CI monitoring, build ops |
| `code-review` | pull requests, commits, compare diff, file diffs, checks/statuses, updates, review comments, review threads, reviewer requests | PR copilots, change summaries |
| `issue-triage` | issues, issue search, labels, comments, reactions, assignees, close/create/update/reopen | support triage, backlog bots |
| `security-audit` | read-only exploration, code and issue search, PR/CI visibility, checks/statuses, compare diff, plus issue creation to report findings | vulnerability scanning, risk reporting |
| `release-manager` | releases, compare diff, commits, workflow runs, pull requests, update/delete releases | changelog generation, release cutting |
| `discussion-moderator` | discussions list/get/comment, plus light issue context | forum / Q&A bots |
| `notification-inbox` | notifications list/mark-read, plus issue, PR, and discussion context | inbox triage (needs a Notifications PAT) |
| `pr-author` | branches (create/delete), file edits, create/update pull requests, review threads, compare | open focused PRs and address review feedback without full maintainer |
| `maintainer` | all tool families including branch creation, forking, repo creation, discussions, notifications, gists, and workflows | full operator workflows with [approval control](/guide/approval-control) |

## Pair presets with token scopes

Each preset maps to specific [GitHub token permissions](/guide/tokens-and-auth):

- `repo-explorer`: read-only token, no write permissions needed (add `discussions: read` for the discussion tools)
- `code-review`: add `pull_requests: write` only if comments or reviewer requests are needed
- `issue-triage`: add `issues: write` (also covers reactions)
- `ci-ops`: add `actions: write` for triggering, cancelling, and re-running workflows
- `security-audit`: read-only token, plus `issues: write` to report findings
- `release-manager`: add `contents: write` for creating releases, `actions: write` if triggering release pipelines
- `discussion-moderator`: add `discussions: write` and `issues: write` for cross-linking replies
- `notification-inbox`: repository read scopes plus a user PAT with the "Notifications" account permission (not available on Connect installation tokens)
- `pr-author`: add `contents: write` and `pull_requests: write`
- `maintainer`: all write scopes, always paired with [approval control](/guide/approval-control); notification tools additionally need a PAT with the "Notifications" account permission

::tip
Default to the smallest preset that can complete the task. Add more capabilities only after your prompt and approval policy are stable.
::
