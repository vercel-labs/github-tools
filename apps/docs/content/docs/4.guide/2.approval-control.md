Write operations like merging a PR or closing an issue can have irreversible consequences. The SDK provides an approval layer that intercepts mutations before they execute.

Configure @github-tools/sdk write safety in this project: use requireApproval on createGithubTools or createGithubAgent so destructive GitHub actions stay human-gated where appropriate. Prefer requireApproval: 'auto' for interactive agents, so routine writes the user asked for skip the prompt. Add guardrails ({ repositories, branches }) so every call stays in the allowed repositories and writes only reach agent branches such as agent/*. Follow https://github-tools.com/guide/approval-control and cross-check the PAT with https://github-tools.com/guide/tokens-and-auth. For durable agents, createDurableGithubAgent pauses the workflow for approval. Auto evaluation is supported by createGithubAgent and the eve extension (https://github-tools.com/frameworks/eve-extension).

::

For TanStack AI, boolean policies use native tool approval. Auto approval uses the GitHub middleware and a shared interrupt registered on the server and client. Follow the [TanStack approval setup](/frameworks/tanstack-ai#enable-jev-auto-modes).

## Require approval for all writes

By default, every write operation requires explicit approval. You don't need to pass any extra option:

```ts [default-approval.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools()
```

## Guardrails

Approval decides whether a person or the evaluation model lets a call run. Guardrails decide where any call may act, whoever approves it. They hold when a person approves too quickly, or when an issue body talks the model into a write:

```ts [guardrails.ts]
import { createGithubAgent } from '@github-tools/sdk'

const agent = createGithubAgent({
  model: 'anthropic/claude-opus-5.5',
  requireApproval: 'auto',
  guardrails: {
    repositories: ['vercel-labs/*'],
    branches: ['agent/*'],
  },
})
```

- `repositories` takes `owner/repo` or `owner/*`, matched regardless of case. A call to any other repository fails, reads included. Tools without a repository target (search, gists, notifications) aren't restricted, so leave them out with a preset or `exclude` if they shouldn't run. `createRepository` and `forkRepository` run only when the new repository's full name matches, so they need `org` or `organization`.
- `branches` takes branch names or patterns where `*` matches any characters, so `agent/*` also matches `agent/fix/flaky-test`. `createBranch`, `deleteBranch`, `createOrUpdateFile` and `editFiles` must name a matching branch; `createOrUpdateFile` without `branch` fails, since it would commit to the default branch. `mergePullRequest` and `enablePullRequestAutoMerge` check the pull request's base branch with one extra request. Opening a pull request into any base stays allowed, so the agent proposes changes and a person merges them.

The checks run before any request reaches GitHub, on the input after `context` defaults. A blocked call fails with `github_tools.GUARDRAIL_BLOCKED` and a reason the model can act on, such as "Writes are limited to branches matching `agent/*`, and `main` doesn't match." Where the integration decides approvals per call, nobody is asked first:

| Integration | A blocked write |
|---|---|
| `createGithubAgent` | Is denied by the approval policy with the reason (`approved: false` on the approval response) |
| `createGithubTools` with `generateText` or `streamText`, and `createDurableGithubAgent` | Skips the approval request, then fails |
| [eve extension](/frameworks/eve-extension) | Is denied with the reason |
| TanStack AI | Asks for approval, then fails |

A merge's base branch is only known once the call runs, so a blocked merge is still asked about first and then fails.

When you build tools from individual factories, wrap the token with `withGithubGuardrails`, and pass `branches` to the merge factories:

```ts [guardrails-factories.ts]
import { createBranch, mergePullRequest, withGithubGuardrails } from '@github-tools/sdk'

const guardrails = { repositories: ['vercel-labs/*'], branches: ['agent/*'] }
const token = withGithubGuardrails(process.env.GITHUB_TOKEN, guardrails)

const tools = {
  createBranch: createBranch(token),
  mergePullRequest: mergePullRequest(token, { branches: guardrails.branches }),
}
```

Guardrails check what the agent asks for. Keep the token's own access narrow as well ([token scopes](/guide/tokens-and-auth)), and protect the default branch with GitHub [branch protection or rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), so a mistake in the agent's configuration can't reach it either.

## Sign approvals

With `useChat` and most chat backends, the client sends the whole conversation on every request, approval responses included. The AI SDK checks a replayed approval against the tool's schema and approval policy, but it can't tell whether a person ever saw it: a request that adds its own approval for `mergePullRequest` merges the pull request.

Pass a secret so the AI SDK signs each approval request it issues and rejects any approval without a valid signature, before the tool runs:

```ts [signed-approvals.ts]
import { createGithubAgent, createGithubTools } from '@github-tools/sdk'
import { createDurableGithubAgent } from '@github-tools/sdk/workflow'
import { streamText } from 'ai'

createGithubAgent({ model, token, experimental_toolApprovalSecret: process.env.TOOL_APPROVAL_SECRET })

// The workflow reads the variable only inside its signing and verification steps.
createDurableGithubAgent({ model, token, experimental_toolApprovalSecret: { environmentVariable: 'TOOL_APPROVAL_SECRET' } })

streamText({ model, tools: createGithubTools({ token }), messages, experimental_toolApprovalSecret: process.env.TOOL_APPROVAL_SECRET })
```

Generate the secret with `openssl rand -base64 32` and give every server instance the same value, since one instance can sign an approval and another verify it. A forged or edited approval throws `AI_InvalidToolApprovalSignatureError`. Use `ai` 7.0.36 or later, which fixed how the signature encodes its fields.

The [eve extension](/frameworks/eve-extension) keeps pending approvals on the server, so it doesn't need this.

## Auto approval

With `requireApproval: 'auto'`, the agent stops asking about routine writes the user clearly asked for:

```ts [auto-approval.ts]
import { createGithubAgent } from '@github-tools/sdk'

const agent = createGithubAgent({
  model: 'anthropic/claude-opus-5.5',
  preset: 'issue-triage',
  requireApproval: 'auto',
})
```

Before each call to a low-risk write tool, a fast evaluation model scores two things. The first is how costly the call would be if it were wrong. The second is whether the latest user message asked for this exact action. The call runs only when both checks pass. Otherwise the user is asked as usual, so a comment the model decided to post because an issue body told it to usually waits for a human. See [Jev](/guide/jev-typesafe-ai) for what the evaluator sees and trusts.

`'auto'` covers labels, assignees, reactions, comments, review-thread replies, reviewer requests, and notification reads (`AUTO_APPROVAL_TOOLS`). Merges, workflow runs, file writes, deletes, releases, and other write tools keep requiring approval. You can opt any single tool in or out:

```ts [auto-approval-per-tool.ts]
createGithubTools({
  requireApproval: {
    addLabels: 'auto',
    addIssueComment: 'auto',
    updateIssue: 'auto',
    mergePullRequest: true,
  },
})
```

Per-tool `'auto'` works on any write tool, including ones outside `AUTO_APPROVAL_TOOLS`. The evaluator then decides alone whether the call runs, so opt in only tools whose mistakes are cheap to undo.

`'auto'` works with `createGithubTools`, `createGithubAgent`, `generateText`, and `streamText`, and needs `ai` 7.0.105 or later. It is not available on `createDurableGithubAgent`.

### Why the agent asks

`createGithubAgent` decides approvals with the AI SDK's call-level `toolApproval`, which replaces tool-level `needsApproval` in AI SDK 7. With `'auto'`, every decision says why:

- **When it asks**, the approval request's `reason` carries the evaluator's verdict, such as "Visible but reversible (risk 0.5 of 2), 1% likely you asked for it." In UI messages it's `part.approval.requestReason`, so an approval prompt can show it.
- **When it lets a call through**, the call is recorded as an automatic approval (`isAutomatic: true`) with a reason such as "Approved automatically: negligible (risk 0.1 of 2), 99% likely you asked for it." The conversation keeps an audit trail of what ran without a person.
- **When the evaluator fails or refuses**, it asks, and the reason says so.

Calls through `callGithubTool` follow the approval of the tool they name. Pass your own `toolApproval` to `createGithubAgent` to replace this policy entirely, for example to deny writes outside an allowed repository with `{ type: 'denied', reason }`. `createGithubTools` keeps tool-level `needsApproval`, so `generateText` and `streamText` work as before, without reasons.

The [eve extension](/frameworks/eve-extension#automatic-presets-and-approval) explains its `'auto'` decisions too. When it asks, the approval prompt ends with the verdict, such as "Add labels on vercel-labs/github-tools#12? Hard to undo (risk 2 of 2), 100% likely you asked for it." When it lets a call through, its approval policy returns `'approved'`, so eve records `clearedBy: { policy: 'approval' }` on the call's `call.started` event, where a call that needed no approval has no `clearedBy`. eve doesn't keep the reason of an automatic approval.

### Tune auto approval

The defaults work without configuration. To change them, use `evaluation`:

```ts [auto-approval-tuning.ts]
createGithubAgent({
  model: 'anthropic/claude-opus-5.5',
  requireApproval: 'auto',
  evaluation: {
    maxRisk: 1, // 0 negligible, 1 visible but reversible, 2 hard to undo
    minIntent: 0.6, // probability the user asked for this exact call
    model: 'typesafe-ai/jev-1.14.0', // any AI SDK decision model
  },
})
```

The values shown are the defaults. The default model is TypeSafe's [Jev](https://vercel.com/i/what-is-jev), called through [AI Gateway](https://vercel.com/docs/ai-gateway/modalities/evaluation). See [Auto presets and approval with Jev](/guide/jev-typesafe-ai) for both `'auto'` modes together.

### When the evaluation model fails

If the evaluation call fails, for example because the model is not enabled for your AI Gateway project, the team is out of credits, or the gateway is rate limiting, the call asks for approval as if `'auto'` were `true`. The agent keeps running, and a `github_tools.EVALUATION_FAILED` warning with the gateway error as `cause` is logged through `console.warn`.

## Disable approval in trusted environments

In CI pipelines or automated workflows where human review happens elsewhere (e.g. PR-based), you can disable approval entirely:

```ts [ci-pipeline.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools({
  requireApproval: false,
})
```

## Configure approval per operation

For nuanced policies, enable approval selectively. This example approves destructive actions but allows comments freely:

```ts [selective-approval.ts]
import { createGithubTools } from '@github-tools/sdk'

const tools = createGithubTools({
  requireApproval: {
    createBranch: false,
    forkRepository: true,
    createRepository: true,
    mergePullRequest: true,
    createOrUpdateFile: true,
    closeIssue: true,
    createPullRequest: false,
    addPullRequestComment: false,
    createIssue: false,
    addIssueComment: false,
  },
})
```

## Override approval per tool

You can also set `needsApproval` via the [`overrides`](/api/reference#tool-overrides) option, which supports all AI SDK tool properties:

```ts [override-approval.ts]
createGithubTools({
  overrides: {
    addIssueComment: { needsApproval: false },
    mergePullRequest: { needsApproval: true },
  },
})
```

When both `requireApproval` and `overrides` set `needsApproval` for the same tool, the `overrides` value wins (it is applied last).

## eve approval (richer policies)

On the [eve extension](/frameworks/eve-extension) (recommended) or the deprecated [direct `/eve` import](/deprecated/eve), `requireApproval` supports boolean gates, `'once'` (approve once per session), string sugar (`'always'` / `'never'`), input-dependent predicates, and passthrough of eve's `always()` / `once()` / `never()` helpers. Write tools default to `always()` when unlisted.

```ts [agent/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'

export default githubExtension({
  preset: 'maintainer',
  requireApproval: {
    mergePullRequest: true,
    createIssue: 'once',
    createOrUpdateFile: ({ toolInput }) => toolInput?.owner !== 'vercel-labs',
  },
})
```

Unlike `createDurableGithubAgent`, eve approval **pauses the session durably** until a person approves.

::warning
Approval is one safety layer, not the only one. Combine it with least-privilege [token scopes](/guide/tokens-and-auth) and narrow [presets](/guide/presets).
::
