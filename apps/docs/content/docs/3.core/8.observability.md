## Overview

GitHub records which identity made a write. It doesn't record who asked the agent for it, or who or what let it run. With `audit`, the [eve extension](/integrations/eve) sends your function a record of each GitHub write that names the agent, the requester, the approver and the target.

The records are plain objects, so the function decides where they go and no logging library is needed. A write is sent to GitHub only after your function accepted the record of the attempt.

`audit` is an option of the eve extension. The AI SDK, TanStack AI and Workflow tools don't have it.

## Record every write

Pass a function as `audit` in the extension's mount file. It receives each record and eve's session context:

```ts [agent/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'
import { db } from '../lib/db'

export default githubExtension({
  connector: 'github/my-connector',
  requireApproval: 'auto',
  audit: record => db.upsert('github_audit', record.id, record),
})
```

`db` stands for your own store. Return once the record is stored, and throw when it can't be. A returned promise is awaited.

The second argument is eve's session context, with `ctx.session.id` and `ctx.session.auth`. A multi-tenant agent uses it to add its tenant to the record before storing it.

## Two records for each write

A write that reaches GitHub has two records with the same `id`:

1. A `started` record, sent after `guardrails` and approval passed and the token resolved, immediately before the request. The write waits for your function.
2. A `settled` record with the `outcome`, sent when eve settles the call.

A write that `guardrails`, an approval policy or a person stopped was never attempted, so it has a `settled` record only.

A store that upserts on `id` holds one row for each write, updated when the outcome arrives. A store that appends holds one row for each record:

| Records for one `id` | Meaning |
| --- | --- |
| `started`, then `settled` | The write was attempted, and this is its outcome |
| `settled` with `outcome: 'denied'` only | The write was stopped before anything was sent |
| `started` only | The write was attempted and its outcome wasn't recorded. GitHub has the answer |

The last row is what a crash or a store outage after the request leaves. Alert on a `started` record that has no `settled` record after its turn ended.

## The record

This is the `settled` record of a merge that a second person approved in Slack:

```json
{
  "id": "wrun_01M75JAWJ2WBT7PZKBP70TDV1E:call_8f2c",
  "phase": "settled",
  "at": "2026-11-11T15:06:31.412Z",
  "tool": "mergePullRequest",
  "target": { "kind": "pull_request", "owner": "acme", "repo": "web", "number": 250 },
  "outcome": "succeeded",
  "agent": { "name": "support-agent" },
  "requester": { "id": "U04A1", "type": "user", "authenticator": "slack" },
  "approver": { "id": "U07B2", "type": "user", "authenticator": "slack" },
  "clearance": "person",
  "githubIdentity": "user",
  "session": { "id": "wrun_01M75JAWJ2WBT7PZKBP70TDV1E", "turnId": "turn_3", "callId": "call_8f2c", "channel": "channel:slack" }
}
```

| Field | Type | Value |
| --- | --- | --- |
| `id` | `string` | The session ID and the call ID. The same in both phases, and each time a record is sent again |
| `phase` | `'started' \| 'settled'` | Which of the two records this is |
| `at` | `string` | ISO 8601 time of this phase: when the record was built for `started`, when eve settled the call for `settled` |
| `tool` | write tool name | The tool, without the mount's prefix, such as `mergePullRequest` |
| `target` | object | What the write acts on, after [`context`](/context) defaults. See [Targets](#targets) |
| `outcome` | `'succeeded' \| 'failed' \| 'denied'` | Set on a `settled` record. See [Outcomes](#outcomes) |
| `reason` | `string` | Why the write was denied or failed. Not set for `succeeded` |
| `agent` | `{ name }` | The eve agent that made the call |
| `requester` | principal | Who drove the turn. Absent when nobody did, as in a scheduled run |
| `approver` | principal | The person who approved the write, or who denied it |
| `clearance` | `'none' \| 'policy' \| 'auto' \| 'person'` | What let the write run, or stopped it. See [Clearance](#clearance) |
| `verdict` | `{ risk, intent }` | The [decision model](/approval#let-a-model-decide)'s answers under `'auto'`: `risk` from 0 to 2 and `intent` from 0 to 1. Set when it rated the write, including when it then asked a person |
| `githubIdentity` | `'app' \| 'user'` | Whose GitHub access the write used: the App installation, or a person's token. Absent when the write was stopped before it ran |
| `session` | `{ id, turnId, callId, channel? }` | The eve session, turn and call. `channel` is eve's channel kind, such as `channel:slack` or `schedule` |
| `reconciled` | `true` | Set on a `settled` record that was delivered after its call settled. See [When the function throws](#when-the-function-throws) |

A principal is `{ id, type, authenticator?, issuer? }`, as the channel authenticated the person: a Slack user ID or a GitHub login, with `type: 'user'` for a person. A person who denied a write they didn't request has no `authenticator`, because eve records the sender of an answer without it.

The agent, the requester and the approver are three fields because they are three roles. The agent chose the call. The requester asked for something in words and may never have asked for this write. A second person may have approved it.

### Targets

`target.kind` comes from the tool, and one more field identifies the target:

| `kind` | Tools | Identified by |
| --- | --- | --- |
| `repository` | `forkRepository`, `createRepository` | `owner` and `repo` |
| `branch` | `createBranch`, `deleteBranch`, `createOrUpdateFile`, `editFiles` | `ref`, the branch name |
| `commit` | `createCommitStatus` | `ref`, the commit SHA |
| `pull_request` | Pull request tools, such as `mergePullRequest` and `addPullRequestComment` | `number` |
| `issue` | Issue tools, such as `addIssueComment` and `addLabels` | `number` |
| `discussion` | `addDiscussionComment` | `number` |
| `comment` | Tools that take a comment ID, such as `updateIssueComment` and `addCommentReaction` | `id` |
| `review_thread` | `resolveReviewThread` | `id` |
| `label` | `createLabel`, `updateLabel`, `deleteLabel` | `name` |
| `release` | `createRelease`, `updateRelease`, `deleteRelease` | `id` |
| `workflow` | `triggerWorkflow` | `id`, the workflow file name or ID |
| `workflow_run` | `cancelWorkflowRun`, `rerunWorkflowRun` | `id` |
| `gist` | Gist tools | `id` |
| `notification` | `markNotificationRead` | `id`, the thread ID |

`owner` and `repo` are set whenever the tool takes a repository. A write that creates its target, such as `createIssue`, has no `number` or `id` in its `started` record. On a `succeeded` record, the target has what GitHub returned: the `number` or `id` of what was created, and its `url`.

A record holds the target and nothing that was written: no title, body, diff or tool input. GitHub keeps the content and its edit history, so your audit store doesn't become a second copy of it.

### Outcomes

| `outcome` | When | `reason` |
| --- | --- | --- |
| `succeeded` | GitHub accepted the write | Not set |
| `failed` | GitHub refused the write, or the call failed before or during the request | The error code, such as `github_tools.FORBIDDEN`. See [Errors](/errors) |
| `denied` | `guardrails`, an approval policy or a person stopped the write | The guardrail's or policy's reason. For a person's denial, the decision model's sentence when it asked them, or eve's "Tool execution was denied." |

### Clearance

| `clearance` | Meaning |
| --- | --- |
| `none` | The write needed no approval |
| `policy` | [`guardrails`](/approval#guardrails) or an approval policy decided, without asking anyone |
| `auto` | The decision model let the write run |
| `person` | A person was asked, by the extension's approval or by an `approval` policy in `agent.ts`. `approver` names who answered |

## When the function throws

Throwing means "not stored", and the two phases handle it differently.

A rejected `started` record stops the write. Nothing is sent to GitHub, and the call fails with [`github_tools.AUDIT_UNAVAILABLE`](/errors#audit), which tells the model not to retry. Reads keep working. An audit store that is down therefore stops the agent's writes, and the error names the cause.

A rejected `settled` record is kept and sent again:

- The extension writes the full record to stderr as one JSON line prefixed `[github-tools] audit`, followed by the error your function threw. Your platform's logs then hold the record even if the store never recovers.
- When a turn of the session ends, the extension sends the records the function rejected again, each with `reconciled: true`. It repeats this at the end of each later turn until the function accepts them.
- A session keeps its newest 100 rejected records for redelivery. Older ones are in the logs only.

The same sweep covers a `settled` record that was never sent because the process stopped between the call and the record. The hooks never fail the turn.

Delivery is at least once, so store records by `id` and `phase`. Each line with the `[github-tools] audit` prefix is one failed delivery, and a rising share of `reconciled` records means the store is slow or failing.

## What has no record

- A read. Only write tools are recorded.
- A dry-run write. With [`dryRun`](/approval#shadow-mode), nothing is written, so nothing is recorded.
- A write that an `approval` policy in `agent.ts` denies. eve doesn't run the extension's own policy for that call, so the extension can't tell that the call is one of its tools. A write that policy sends to a person is recorded.
- The outcome of a call eve interrupts or abandons. A cancelled turn or a crash during a write leaves the `started` record without a `settled` one. If the model repeats the write after a crash, the new call has its own `id` and records.

A call that waits for a sign-in and runs again sends its `started` record a second time, with the same `id`.

## FAQ

::accordion

:::accordion-item{label="Do I need a logging library?"}
No. A record is a plain object typed as `GithubAuditRecord`, exported from `@github-tools/sdk/eve-runtime`. To use a logging library, map the record in your function.
:::

:::accordion-item{label="How much does it add to a write?"}
Two calls to your function for each write that reaches GitHub. The first one is awaited before the request, so its latency is added to the write.
:::

:::accordion-item{label="What does a mount without audit cost?"}
One check for each call. Without `audit`, the extension keeps no session state and sends nothing.
:::

:::accordion-item{label="I mount the extension twice. Which function gets a record?"}
Each mount has its own `audit` function and records the writes of its own tools only.
:::

:::accordion-item{label="Does a record hold personal data?"}
It holds the principal IDs of the requester and the approver as the channel authenticated them, and no email, name or message text. If you handle erasure requests, apply your store's policy to `requester` and `approver`.
:::

:::accordion-item{label="Are writes through eve__tool recorded?"}
Yes. A deferred tool that the model reaches through `eve__tool` is recorded like a listed one.
:::
