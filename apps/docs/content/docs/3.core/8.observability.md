## Overview

With `audit`, the [eve extension](/integrations/eve) sends your function a record of every GitHub write an agent makes. A record names the agent, the person who asked, the person or policy that let the write run, the target and the outcome.

GitHub's own audit log shows which identity made a write. It doesn't show who asked the agent for it, or what approved it. The records answer questions such as these:

- Who approved the merge of pull request 250, and who asked for it?
- Which writes did the agent try that `guardrails` blocked?
- Which writes ran without asking anyone, and what let them through?
- Does every write the agent attempted have an outcome?

A record is a plain object. Your function decides where it goes, so no logging library is required and any library works. A write is sent to GitHub only after your function accepted the record of the attempt.

`audit` is an option of the eve extension. The AI SDK, TanStack AI and Workflow tools don't have it.

## Record every write

Pass a function as `audit` in the extension's mount file. This function prints each record as one JSON line, which is enough to see the records in your terminal and in your platform's logs:

```ts [agent/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'

export default githubExtension({
  connector: 'github/my-connector',
  requireApproval: 'auto',
  audit: record => console.log(JSON.stringify(record)),
})
```

When the agent comments on an issue, the function is called twice for that write. The first call happens before the request, and the second one carries the outcome:

Both records say that a person asked in Slack, that the decision model let the comment through, and that it was posted with the GitHub App's access.

The function takes two arguments:

- `record` is a `GithubAuditRecord`. [The record](#the-record) lists its fields.
- `ctx` is eve's session context, with `ctx.session.id` and `ctx.session.auth`. Use it to add what only your agent knows, such as a tenant.

What the function does with the record tells the extension whether the record is stored:

| The function | Means | The extension then |
| --- | --- | --- |
| Returns, or resolves its promise | The record is stored | Sends the write, or moves on after an outcome |
| Throws, or rejects its promise | The record isn't stored | Stops the write for a `started` record, and sends a `settled` record again later. See [When the function throws](#when-the-function-throws) |

`console.log` never throws, so the function above never stops a write. Use a store that can fail, as in the next section, when no write may happen without a stored record.

## Send the records to a destination

The examples below move the function to its own file and type its argument. To import the `GithubAuditRecord` type there, add the SDK to your agent:

:::code-group
```bash [pnpm]

```
```bash [npm]

```
```bash [yarn]

```


### Store the records in Postgres

A table keyed by `id` and `phase` holds one row for each record. Delivery is at least once, so the same record can arrive again, and the `on conflict` clause makes that harmless:

```sql [schema.sql]
create table github_audit (
  id text not null,
  phase text not null,
  at timestamptz not null,
  tool text not null,
  outcome text,
  record jsonb not null,
  primary key (id, phase)
);
```

```ts [agent/lib/audit-store.ts]
import type { GithubAuditRecord } from '@github-tools/sdk/eve-runtime'
import postgres from 'postgres'

const sql = postgres(process.env.DATABASE_URL!)

export async function storeAuditRecord(record: GithubAuditRecord) {
  await sql`
    insert into github_audit (id, phase, at, tool, outcome, record)
    values (${record.id}, ${record.phase}, ${record.at}, ${record.tool}, ${record.outcome ?? null}, ${sql.json(record)})
    on conflict (id, phase) do update
      set at = excluded.at, outcome = excluded.outcome, record = excluded.record
  `
}
```

```ts [agent/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'
import { storeAuditRecord } from '../lib/audit-store'

export default githubExtension({
  connector: 'github/my-connector',
  requireApproval: 'auto',
  audit: storeAuditRecord,
})
```

The example uses the [`postgres`](https://github.com/porsager/postgres) client. When the insert fails, `storeAuditRecord` rejects, so a database outage stops the agent's writes instead of letting them run unrecorded.

The table then answers the questions from the overview. This query lists who asked for and who approved each merge:

```sql
select at,
       record->'requester'->>'id' as requester,
       record->'approver'->>'id' as approver,
       record->'target'->>'url' as pull_request
from github_audit
where phase = 'settled' and tool = 'mergePullRequest' and outcome = 'succeeded'
order by at desc;
```

This query lists the writes that `guardrails` or an approval policy stopped without asking anyone. A write the agent tried and wasn't allowed to make is the first place to look for a prompt injection:

```sql
select at, tool, record->'target' as target, record->>'reason' as reason
from github_audit
where outcome = 'denied' and record->>'clearance' = 'policy'
order by at desc;
```

This query lists the writes that were attempted and have no outcome after ten minutes. Run it on a schedule and alert on its rows:

```sql
select started.id, started.tool, started.at, started.record->'target' as target
from github_audit started
left join github_audit settled on settled.id = started.id and settled.phase = 'settled'
where started.phase = 'started'
  and settled.id is null
  and started.at < now() - interval '10 minutes';
```

### Send the records to evlog

[evlog](https://evlog.dev) has an audit model of its own: a wide event with an `audit` field that holds an action, an actor, a target and an outcome. Its drains can route those events to a dedicated or signed store. Install it in your agent:

:::code-group
```bash [pnpm]
pnpm add evlog
```
```bash [npm]
npm install evlog
```
```bash [yarn]
yarn add evlog
```
```bash [bun]
bun add evlog
```
:::

This function maps each outcome record to one evlog audit event. The agent is the actor, and what evlog's audit fields have no place for goes under `github` on the same event:

```ts [agent/lib/audit-evlog.ts]
import type { GithubAuditRecord } from '@github-tools/sdk/eve-runtime'
import { createLogger } from 'evlog'

const OUTCOMES = { succeeded: 'success', failed: 'failure', denied: 'denied' } as const

function targetId({ owner, repo, number, ref, name, id }: GithubAuditRecord['target']) {
  const repository = owner && repo ? `${owner}/${repo}` : undefined
  return [repository, number ?? ref ?? name ?? id].filter(part => part !== undefined).join('#')
}

export function auditWithEvlog(record: GithubAuditRecord) {
  // evlog's audit outcome has no value for a write that hasn't finished.
  if (!record.outcome) return
  const { at, requester, approver, clearance, verdict, githubIdentity, session, reconciled } = record
  const log = createLogger({ github: { at, requester, approver, clearance, verdict, githubIdentity, session, reconciled } })
  log.audit({
    action: `github.${record.tool}`,
    actor: { type: 'agent', id: record.agent.name },
    target: { type: record.target.kind, id: targetId(record.target), url: record.target.url },
    outcome: OUTCOMES[record.outcome],
    reason: record.reason,
    correlationId: record.id,
  })
  log.emit()
}
```

Sending records to evlog differs from writing to your own store in two ways:

- `started` records are skipped. evlog's audit `outcome` is `success`, `failure` or `denied`, so a write that hasn't finished has no value there.
- A write doesn't wait for storage. `log.emit()` returns before the drains have stored the event, and a drain that fails logs `[evlog] drain failed` without making the function throw.

The function assumes evlog is already set up in your agent with a drain. To keep audit events in their own tamper-evident store, wrap a drain in evlog's `auditOnly` and `signed`, as [evlog's audit guide](https://www.evlog.dev/use-cases/audit/overview) describes.

### Use several destinations

To keep "no write without a stored record" and still send events to evlog, call your own store first. When the store rejects the record, the function throws before evlog gets anything:

```ts [agent/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'
import { auditWithEvlog } from '../lib/audit-evlog'
import { storeAuditRecord } from '../lib/audit-store'

export default githubExtension({
  connector: 'github/my-connector',
  requireApproval: 'auto',
  audit: async (record) => {
    await storeAuditRecord(record)
    auditWithEvlog(record)
  },
})
```

Put the destination that must not miss a record first. A destination that throws after another one accepted the record makes the extension send that record again, so every destination has to accept a record it already has.

### Add a tenant

The extension doesn't know which tenant a session belongs to. Read it from `ctx`, the function's second argument, and store it with the record:

```ts [agent/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'

export default githubExtension({
  connector: 'github/my-connector',
  audit: (record, ctx) => db.insert('github_audit', { ...record, tenant: tenantOf(ctx.session.auth.current) }),
})
```

`db` and `tenantOf` stand for your own store and your own lookup from the caller eve authenticated.

## Two records for each write

A write that reaches GitHub has two records with the same `id`:

1. A `started` record, sent after `guardrails` and approval passed and the token resolved, immediately before the request. The write waits for your function.
2. A `settled` record with the `outcome`, sent when eve settles the call.

A write that `guardrails`, an approval policy or a person stopped was never attempted, so it has a `settled` record only.

What a store holds for one `id` tells you what happened to the write:

| Records for one `id` | Meaning |
| --- | --- |
| `started`, then `settled` | The write was attempted, and this is its outcome |
| `settled` with `outcome: 'denied'` only | The write was stopped before anything was sent |
| `started` only | The write was attempted and its outcome wasn't recorded. GitHub has the answer |

The last row is what a crash or a store outage after the request leaves. The record still says where to look, which is why the attempt is recorded before the request.

## The record

| Field | Type | Value |
| --- | --- | --- |
| `id` | `string` | The session ID and the call ID. The same in both phases, and each time a record is sent again |
| `phase` | `'started' \| 'settled'` | Which of the two records this is |
| `at` | `string` | ISO 8601 time of this phase. For `started`, when the record was built. For `settled`, when eve settled the call |
| `tool` | write tool name | The tool, without the mount's prefix, such as `mergePullRequest` |
| `target` | object | What the write acts on, after [`context`](/context) defaults. See [Targets](#targets) |
| `outcome` | `'succeeded' \| 'failed' \| 'denied'` | Set on a `settled` record. See [Outcomes](#outcomes) |
| `reason` | `string` | Why the write was denied or failed. Not set for `succeeded` |
| `agent` | `{ name }` | The eve agent that made the call |
| `requester` | principal | Who drove the turn. Absent when nobody did, as in a scheduled run |
| `approver` | principal | The person who approved the write, or who denied it |
| `clearance` | `'none' \| 'policy' \| 'auto' \| 'person'` | What let the write run, or stopped it. See [Clearance](#clearance) |
| `verdict` | `{ risk, intent }` | The [decision model](/approval#let-a-model-decide)'s answers under `'auto'`, with `risk` from 0 to 2 and `intent` from 0 to 1. Set when the model rated the write, including when it then asked a person |
| `githubIdentity` | `'app' \| 'user'` | Whose GitHub access the write used, the App installation's or a person's token. Absent when the write was stopped before it ran |
| `session` | `{ id, turnId, callId, channel? }` | The eve session, turn and call. `channel` is eve's channel kind, such as `channel:slack` or `schedule` |
| `reconciled` | `true` | Set on a `settled` record that was delivered after its call settled. See [When the function throws](#when-the-function-throws) |

A principal is `{ id, type, authenticator?, issuer? }`, as the channel authenticated the person. `id` is the channel's ID for them, such as a Slack user ID, and `type` is `'user'` for a person. A person who denied a write they didn't request has no `authenticator`, because eve records the sender of an answer without it.

The agent, the requester and the approver are three fields because they are three roles. The agent chose the call. The requester asked for something in words and may never have asked for this write. A second person may have approved it.

### Targets

`target.kind` comes from the tool, and one more field identifies the target:

| `kind` | Tools | Identified by |
| --- | --- | --- |
| `repository` | `forkRepository`, `createRepository` | `owner` and `repo` |
| `branch` | `createBranch`, `deleteBranch`, `createOrUpdateFile`, `editFiles` | `ref`, the branch name |
| `commit` | `createCommitStatus` | `ref`, the commit SHA |
| `pull_request` | Pull request tools, such as `mergePullRequest` and `addPullRequestComment` | `number` |
| `issue` | Issue tools, such as `addIssueComment` and `addLabels` | `number` |
| `discussion` | `addDiscussionComment` | `number` |
| `comment` | Tools that take a comment ID, such as `updateIssueComment` and `addCommentReaction` | `id` |
| `review_thread` | `resolveReviewThread` | `id` |
| `label` | `createLabel`, `updateLabel`, `deleteLabel` | `name` |
| `release` | `createRelease`, `updateRelease`, `deleteRelease` | `id` |
| `workflow` | `triggerWorkflow` | `id`, the workflow file name or ID |
| `workflow_run` | `cancelWorkflowRun`, `rerunWorkflowRun` | `id` |
| `gist` | Gist tools | `id` |
| `notification` | `markNotificationRead` | `id`, the thread ID |

`owner` and `repo` are set whenever the tool takes a repository. A write that creates its target, such as `createIssue`, has no `number` or `id` in its `started` record. On a `succeeded` record, the target has what GitHub returned, which is the `number` or `id` of what was created and its `url`.

A record holds the target and nothing that was written. It has no title, body, diff or tool input. GitHub keeps the content and its edit history, so your audit store doesn't become a second copy of it.

### Outcomes

| `outcome` | When | `reason` |
| --- | --- | --- |
| `succeeded` | GitHub accepted the write | Not set |
| `failed` | GitHub refused the write, or the call failed before or during the request | The error code, such as `github_tools.FORBIDDEN`. See [Errors](/errors) |
| `denied` | `guardrails`, an approval policy or a person stopped the write | The guardrail's or policy's reason. For a person's denial, the decision model's sentence when it asked them, or eve's "Tool execution was denied." |

### Clearance

| `clearance` | Meaning |
| --- | --- |
| `none` | The write needed no approval |
| `policy` | [`guardrails`](/approval#guardrails) or an approval policy decided, without asking anyone |
| `auto` | The decision model let the write run |
| `person` | A person was asked, by the extension's approval or by an `approval` policy in `agent.ts`. `approver` names who answered |

## When the function throws

Throwing means "not stored", and the extension handles it differently for each phase:

| The function throws on | The write | The record |
| --- | --- | --- |
| A `started` record | Isn't sent. The call fails with [`github_tools.AUDIT_UNAVAILABLE`](/errors#audit), which tells the model not to retry | Is written to stderr. The call's `settled` record follows, with `outcome: 'failed'` |
| A `settled` record | Already happened, or was already stopped | Is written to stderr, kept in the session, and sent again |

Reads keep working in both cases. An audit store that is down therefore stops the agent's writes, and the error names the cause.

A `settled` record the function rejects goes through these steps:

1. The extension writes the full record to stderr as one JSON line prefixed `[github-tools] audit`, followed by the error your function threw. Your platform's logs then hold the record even if the store never recovers.
2. When a turn of the session ends, the extension sends the record again, with `reconciled: true`.
3. The extension repeats the second step at the end of each later turn, until the function accepts the record.

The record's line in the logs looks like this:

```text
[github-tools] audit {"id":"wrun_01M75JAWJ2WBT7PZKBP70TDV1E:call_8f2c","phase":"settled","at":"2026-11-11T15:06:31.412Z","tool":"addIssueComment","target":{"kind":"issue","owner":"acme","repo":"web","number":812,"url":"https://github.com/acme/web/issues/812#issuecomment-2471"},"outcome":"succeeded","agent":{"name":"support-agent"},"requester":{"id":"U04A1B2C3","type":"user","authenticator":"slack-webhook"},"clearance":"auto","verdict":{"risk":0.1,"intent":0.92},"githubIdentity":"app","session":{"id":"wrun_01M75JAWJ2WBT7PZKBP70TDV1E","turnId":"turn_3","callId":"call_8f2c","channel":"channel:slack"}}
```

A session keeps its newest 100 rejected records for redelivery, and older ones are in the logs only. The same sweep sends a `settled` record that was never sent because the process stopped between the call and the record. The extension's hooks never fail the turn.

Delivery is at least once, so store records by `id` and `phase`. Each line that starts with `[github-tools] audit {` is one failed delivery, and a rising share of `reconciled` records means the store is slow or failing.

## What has no record

- A read. Only write tools are recorded.
- A dry-run write. With [`dryRun`](/approval#shadow-mode), nothing is written, so nothing is recorded.
- A write that an `approval` policy in `agent.ts` denies. eve doesn't run the extension's own policy for that call, so the extension can't tell that the call is one of its tools. A write that policy sends to a person is recorded.
- The outcome of a call eve interrupts or abandons. A cancelled turn or a crash during a write leaves the `started` record without a `settled` one. If the model repeats the write after a crash, the new call has its own `id` and records.

A call that waits for a sign-in and runs again sends its `started` record a second time, with the same `id`.

## FAQ

::accordion

:::accordion-item{label="Do I need a logging library?"}
No. A record is a plain object, and a function that inserts it into your database is enough. To use a library, map the record in your function, as in [Send the records to evlog](#send-the-records-to-evlog).
:::

:::accordion-item{label="How much does it add to a write?"}
Two calls to your function for each write that reaches GitHub. The first one is awaited before the request, so its latency is added to the write.
:::

:::accordion-item{label="Can a slow store hold up a write?"}
Yes. The write waits for as long as the function takes on the `started` record. To bound that, reject after a timeout in your function, which stops the write like any other rejected `started` record.
:::

:::accordion-item{label="What does a mount without audit cost?"}
One check for each call. Without `audit`, the extension keeps no session state and sends nothing.
:::

:::accordion-item{label="I mount the extension twice. Which function gets a record?"}
Each mount has its own `audit` function and records the writes of its own tools only.
:::

:::accordion-item{label="Does a record hold personal data?"}
It holds the principal IDs of the requester and the approver as the channel authenticated them, and no email, name or message text. If you handle erasure requests, apply your store's policy to `requester` and `approver`.
:::

:::accordion-item{label="Are writes through eve__tool recorded?"}
Yes. A deferred tool that the model reaches through `eve__tool` is recorded like a listed one.
:::

::
