The manager holds no GitHub tools. It reads the request, hands it to the right specialist, and combines the answers. Ask "review #42 and check whether the changelog needs updating" and it calls `reviewer` for the pull request and `releaser` for the changelog. Each specialist lists only its preset's tools and has its own approval policy, so no single context carries all 91 tools.

## Files

```text
agent/
├── agent.ts                     # defineAgent({ model }), no GitHub extension
├── instructions.md              # routing rules
└── subagents/
    ├── reviewer/
    │   ├── agent.ts             # description + model
    │   ├── instructions.md
    │   └── extensions/github.ts # preset: 'code-review'
    ├── triager/
    │   ├── agent.ts
    │   ├── instructions.md
    │   └── extensions/github.ts # preset: 'issue-triage'
    └── releaser/
        ├── agent.ts
        ├── instructions.md
        └── extensions/github.ts # preset: 'release-manager'
```

eve turns each directory under `agent/subagents/` into a tool named after it. The manager's model calls `reviewer` with `{ message }`, and the subagent's final reply comes back as the result. A [declared subagent](https://eve.dev/docs/subagents#the-isolation-boundary) inherits nothing from the root, so each one mounts its own copy of the extension.

### The manager

```md [agent/instructions.md]
You are the GitHub manager for this repository. You never call GitHub tools yourself.
You have three specialists: reviewer, triager, and releaser.

- Pull request reviews, diffs, or code quality: call reviewer.
- Issue classification, labels, or backlog questions: call triager.
- Changelogs, release notes, or what changed since the last release: call releaser.
- When a request spans several specialists, call each and combine their answers.
- Put everything a specialist needs in its message. It never sees this conversation.
```

### A specialist

The reviewer is three files. `description` is required: the manager's model reads it to decide when to delegate.

```ts [agent/subagents/reviewer/agent.ts]
import { defineAgent } from 'eve'

export default defineAgent({
  description: 'Reviews pull requests: reads diffs and CI status, and drafts review comments.',
  model: 'anthropic/claude-opus-5.5',
})
```

```ts [agent/subagents/reviewer/extensions/github.ts]
import githubExtension from '@github-tools/eve-extension'

export default githubExtension({
  connector: 'github/my-connector',
  preset: 'code-review',
})
```

```md [agent/subagents/reviewer/instructions.md]
You review pull requests. Read the description and the changed files, check for bugs
and missing edge cases, and reply with a short, actionable summary.
```

The other two follow the same shape:

| Subagent | `preset` | `description` | `requireApproval` |
| --- | --- | --- | --- |
| `triager` | `issue-triage` | Triages issues: classifies, labels, and comments with a next step | `{ addLabels: false, addIssueComment: false }` |
| `releaser` | `release-manager` | Summarizes changes since the last release and drafts release notes | default: every write asks |

Approvals from a subagent appear on the manager's session, so the person talking to the manager answers them. `requireApproval: 'auto'` doesn't help here: inside a subagent session the latest message comes from the manager, not a person, so every write keeps asking.

```bash [pnpm]
pnpm add @github-tools/eve-extension @vercel/connect eve ai zod
```
```bash [npm]
npm install @github-tools/eve-extension @vercel/connect eve ai zod
```
```bash [yarn]
yarn add @github-tools/eve-extension @vercel/connect eve ai zod
```
```bash [bun]
bun add @github-tools/eve-extension @vercel/connect eve ai zod
```
:::

Create a connector named `github/my-connector` and pull its token as [Auth](/auth#create-a-github-connector) describes. All three specialists share it here; give each its own connector, or `connect: { repositories: [...] }`, when they should reach different repositories.

## Run it

```bash [Terminal]
npx eve dev
```

Ask "review vercel-labs/github-tools#42 and check whether the changelog needs updating for the next release". The manager calls `reviewer` and `releaser`, then answers with both results.

## Without eve

With the AI SDK, wrap each `createGithubAgent` in a tool and give the tools to a manager `ToolLoopAgent`:

```ts [manager.ts]
import { createGithubAgent, type GithubToolPreset } from '@github-tools/sdk'
import { connectGithubToken } from '@github-tools/sdk/connect'
import { ToolLoopAgent, tool } from 'ai'
import { z } from 'zod'

function specialist(preset: GithubToolPreset, description: string) {
  const agent = createGithubAgent({
    model: 'anthropic/claude-opus-5.5',
    token: connectGithubToken('github/my-connector', { preset }),
    preset,
  })
  return tool({
    description,
    inputSchema: z.object({ message: z.string().describe('Everything the specialist needs to do the task') }),
    execute: async ({ message }) => (await agent.generate({ prompt: message })).text,
  })
}

export const manager = new ToolLoopAgent({
  model: 'anthropic/claude-opus-5.5',
  instructions: 'Route GitHub requests to the right specialist: reviewer, triager, or releaser.',
  tools: {
    reviewer: specialist('code-review', 'Reviews pull requests and drafts review comments.'),
    triager: specialist('issue-triage', 'Classifies and labels GitHub issues.'),
    releaser: specialist('release-manager', 'Drafts release notes from merged pull requests.'),
  },
})
```

Here a write that needs approval ends the specialist's turn, and its request stays inside that agent instead of reaching the manager's caller. Keep the specialists to reads, or set `requireApproval: false` only where a person reviews the result anyway.

## Go further

Add a `security-audit` subagent for vulnerability reports, or set `tool: 'deferred'` in a subagent's `agent.ts` so the manager finds it with `eve__search` instead of listing it on every call.
