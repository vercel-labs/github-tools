Octokit and the gh CLI call the GitHub API on behalf of code or a person, while GitHub tools turns those API calls into typed tools that a model chooses and fills in. GitHub tools uses Octokit underneath, and adds what an agent needs on top: input schemas, approval before writes, results trimmed for a model, and errors the model can act on.

## What each one is

**[Octokit](https://github.com/octokit/octokit.js)** is GitHub's JavaScript SDK. Your code picks each endpoint and its parameters, such as `octokit.rest.issues.addLabels(...)`, and gets GitHub's full response back. There is no model in the loop unless you put one there.

**The [gh CLI](https://cli.github.com)** is GitHub's command-line tool. An agent uses it through a shell tool: the model writes a command such as `gh issue list --label bug --json number,title`, your code runs it, and the model reads the text output.

**GitHub tools** gives the model 91 named tools, such as `listIssues` and `addLabels`, each with a Zod input schema and a shaped result. The model picks the tool and fills its input, and your code decides which calls wait for a person.

## Comparison

| | GitHub tools | Octokit | gh CLI through a shell tool |
| --- | --- | --- | --- |
| Who picks the call | The model, from tool descriptions | Your code | The model, as a command string |
| Input checking | A Zod schema per tool, checked before the call | TypeScript types at build time | The CLI's flag parsing at run time |
| Approval | Per write tool, on by default. See [Approval](/approval) | None: your code runs what it calls | Whatever your shell tool asks, per command string |
| Scoping | [Presets](/presets) and the token's permissions | The token's permissions | The token's permissions, plus anything else the shell can run |
| Output size | Shaped results with paging, bodies cut to about 500 characters | GitHub's full response | Text, or the fields the model lists in `--json` |
| Errors | A code, cause and fix the model can read. See [Errors](/errors) | Exceptions with GitHub's status and message | Text on stderr and an exit code |
| Auth | A token, a function per call, or [Vercel Connect](/auth#vercel-connect) | A token or a GitHub App | `gh auth login` or `GH_TOKEN` |
| Runtime | Any Node.js process | Any JavaScript runtime | A shell with `gh` installed, ideally a sandbox |

## When to pick each

Pick **GitHub tools** when a model decides what to do on GitHub: an agent that reviews, triages or reports. The schemas keep the model's input valid, approval keeps writes in front of a person, and the trimmed results keep context for the task.

Pick **Octokit** when your code already knows the call to make. A webhook handler that checks a commenter's permission, a script that copies labels between repositories, or a step before or after the agent doesn't need a model to choose the endpoint.

Pick **the gh CLI** when the agent already works in a shell, such as a coding agent in a sandbox, and needs a GitHub operation that no tool covers. `gh api` reaches any REST or GraphQL endpoint. Approval is then per command, so a person reads a command string rather than a tool name and typed input.

## Use Octokit next to GitHub tools

`createOctokit` from `@github-tools/sdk` returns the same Octokit client the tools use: it sends the GitHub API version the tools are built against and turns failures into the same [error codes](/errors). `resolveGithubToken` resolves the token the same way as the tools, from `GITHUB_TOKEN`, a string, a function or a Vercel Connect token.

Use them to write a tool for an endpoint GitHub tools doesn't cover, and give the model both:

```ts [contributors.ts]
import { createGithubTools, createOctokit, resolveGithubToken } from '@github-tools/sdk'
import { generateText, stepCountIs, tool } from 'ai'
import { z } from 'zod'

const listContributors = tool({
  description: 'List the top contributors to a repository, by number of commits',
  inputSchema: z.object({
    owner: z.string().describe('Repository owner'),
    repo: z.string().describe('Repository name'),
  }),
  execute: async ({ owner, repo }) => {
    const octokit = createOctokit(await resolveGithubToken())
    const { data } = await octokit.rest.repos.listContributors({ owner, repo, per_page: 10 })
    return data.map(user => ({ login: user.login, contributions: user.contributions }))
  },
})

const { text } = await generateText({
  model: 'anthropic/claude-opus-5.5',
  tools: { ...createGithubTools({ preset: 'repo-explorer' }), listContributors },
  stopWhen: stepCountIs(5),
  prompt: 'Who are the top contributors to vercel/ai, and which open pull requests are theirs?',
})
```

The tool returns two fields per contributor instead of GitHub's full user objects, the same way the built-in tools shape their results. If it writes to GitHub, set `needsApproval: true` on it so it asks like the built-in writes.

The [pull request review guide](/guides/review-pull-requests#_2-scope-the-token-to-one-repository) uses `createOctokit` the other way: plain code that checks a commenter's permission before the agent runs.

## FAQ

::accordion

:::accordion-item{label="Does GitHub tools use Octokit?"}
Yes. Every tool calls GitHub through the `octokit` package: the REST API for most tools, and GraphQL for a few, such as discussions and review threads. Each returns a shaped result instead of the raw response.
:::

:::accordion-item{label="Can I get the raw GitHub response from a tool?"}
No. Tools return the fields a model needs. Call the endpoint with `createOctokit` when your code needs the full response.
:::

:::accordion-item{label="Is it safe to give an agent the gh CLI?"}
It depends on the shell. A shell tool can run any command, not only `gh`, so run it in a sandbox, keep the token narrow, and approve commands before they run. GitHub tools limits the model to named operations without a shell.
:::

:::accordion-item{label="Can a tool I write with Octokit fail like the built-in tools?"}
Yes. Calls through `createOctokit` already fail with the same codes, and `githubToolsErrors` builds the same errors for your own checks. See [Errors](/errors#fail-the-same-way-in-your-own-tools).
:::
