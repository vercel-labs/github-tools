To test an eve agent that uses the GitHub tools, start a GitHub emulator from the eval run's `setup`, create the issue or pull request the eval is about, send the agent a message as a named person, and assert on what the emulator holds afterward. No request reaches `api.github.com` or `api.vercel.com`, so an eval needs no token, comments on no real issue, and gives the same result on every run. This guide adds evals to an agent built on the [eve extension](/integrations/eve).

The emulator is [`vercel-labs/emulate`](https://github.com/vercel-labs/emulate), a stateful GitHub emulator. `@github-tools/eve-extension/testing` starts it with what emulate doesn't have: the routes and GraphQL queries the tools call, the role checks GitHub makes for a personal token, and a Vercel Connect emulator that issues its tokens. All 97 tools run against it.

## What you'll build

An `evals/` folder for your agent with two kinds of eval:

- A behavior eval: bob, who has Read, opens an issue. alice, who has Write, asks the agent to triage it. The eval reads the issue back from the emulator and checks its labels.
- A channel eval: a comment created in the emulator reaches the agent as a signed webhook, and the eval reads the agent's reply from the thread.

## Before you start

- An eve agent that mounts `@github-tools/eve-extension`, on eve 1.0.0-rc.6 or later and Node.js 24.
- eve's [evals](https://eve.dev/docs/evals) run from an `evals/` folder with `npx eve eval`. An eval that calls a real model needs the model's credentials. Nothing else needs one.

## 1. Install the emulator

The emulator is a development dependency of your agent:

:::code-group
```bash [pnpm]
pnpm add -D @emulators/core@0.13.1 @emulators/github@0.13.1
```
```bash [npm]
npm install -D @emulators/core@0.13.1 @emulators/github@0.13.1
```
```bash [yarn]
yarn add -D @emulators/core@0.13.1 @emulators/github@0.13.1
```
```bash [bun]
bun add -d @emulators/core@0.13.1 @emulators/github@0.13.1
```
:::

The extension is tested against this exact version, so keep the pin.

## 2. Start the emulators

`emulateGithub` starts a GitHub emulator and a Vercel Connect emulator on loopback ports. Call it from `setup`, which eve runs once, before it starts the agent:

```ts [evals/evals.config.ts]
import { defineEvalConfig } from 'eve/evals'
import { emulateGithub } from '@github-tools/eve-extension/testing'

export default defineEvalConfig({
  setup: () => emulateGithub({
    repositories: { 'acme/web': { labels: ['bug', 'docs'] } },
    people: { alice: { role: 'write' }, bob: { role: 'read' } },
  }),
  teardown: context => context?.close(),
})
```

- `repositories` are created with a README on `main`. An owner named in `people` is that user, and any other owner is an organization.
- `people` are GitHub users. `role` is their role on every repository: `'read'`, `'triage'`, `'write'`, `'maintain'`, or `'admin'`. A person with no `role` is a GitHub user with no access beyond what a public repository gives everyone.
- One GitHub App, `eve-agent`, is installed on every owner with the permissions the tools use. It is the agent's bot.

The return value is `t.context` in every eval. `emulateGithub` also points the agent at the emulators: it sets `NODE_OPTIONS` so that Node loads a `fetch` redirect in the agent's thread, and it sets `GITHUB_TOKEN`, the GitHub App variables eve's GitHub channel reads, and a placeholder `VERCEL_OIDC_TOKEN`. Your agent files don't import the redirect, and nothing of it is in a production build.

Both emulators listen on loopback only, answer no request a web page sends, and give each person a token that differs on every run.

If the agent's thread starts without the redirect, the run stops before the first eval and the error names the cause. Without that check, the agent would send the emulators' tokens to the real hosts.

## 3. Say who is asking

Approval, `actAs`, and `respondTo` depend on who is talking to the agent. Add `evalIdentity()` to the eve channel's auth:

```ts [agent/channels/eve.ts]
import { eveChannel } from 'eve/channels/eve'
import { evalIdentity } from '@github-tools/eve-extension/testing/agent'

export default eveChannel({ auth: [evalIdentity(), /* your production auth */] })
```

`evalIdentity()` accepts what eve's `localDev()` accepts: a request to a local development server, from a loopback host. It then names the caller from the `x-eval-user` header. In production it accepts nothing, and your own auth decides.

In an eval, `as('alice')` returns the request options that send that header. Pass it to `t.send` and to `session.respond`:

```ts
const turn = await t.send('Triage acme/web#12', as('alice'))
```

A person is two things with one name: the eve principal `alice`, and the GitHub user `alice`. With [`actAs: 'user'` or `'caller'`](/integrations/eve#per-user-tokens), the extension asks Vercel Connect for alice's token, and the Connect emulator answers with one the GitHub emulator knows as her.

## 4. Write an eval

An eval arranges state as one person, sends a message as another, and asserts on the emulator:

```ts [evals/triage.eval.ts]
import { defineEval } from 'eve/evals'
import { includes } from 'eve/evals/expect'
import { as } from '@github-tools/eve-extension/testing'
import type config from './evals.config'

export default defineEval<typeof config>({
  async test(t) {
    const web = t.context.github.repo('acme/web')
    const issue = await web.as('bob').createIssue({ title: 'Crash on save', body: 'TypeError: cannot read properties of undefined' })

    const turn = await t.send(`Triage acme/web#${issue.number}`, as('alice'))

    turn.calledTool('github__addLabels')
    t.check((await web.issue(issue.number)).labels, includes('bug'))
  },
})
```

Run it:

```bash
npx eve eval
```

Evals run eight at a time and share one emulator. Create the issue or pull request an eval works on inside that eval, and use the number you get back, so two evals never share an item. An eval that changes repository-level state, such as labels, creates its own repository with `await t.context.github.createRepo('acme')`.

### Check who can do what

The emulator refuses a call the way GitHub does, so an eval can assert the refusal. bob has Read, and labeling needs Triage:

```ts [evals/reader.eval.ts]
const asked = await t.send(`label acme/web#${issue.number}`, as('bob'))
const answered = await asked.session.respond([{ interactionId: asked.interactions[0]!.interactionId, optionId: 'approve' }], as('bob'))

answered.calledTool('github__addLabels', { status: 'failed', count: 1 })
t.check(answered.reply, includes('github_tools.FORBIDDEN'))
```

Where GitHub accepts a request and ignores part of it, the emulator does the same. A person without Triage can open an issue or edit their own, and GitHub drops the labels, assignees, and milestone they send. It also answers their request to assign someone with success and assigns nobody. The tool call completes in both cases, so assert on the issue and not on the call:

```ts
t.check((await web.issue(issue.number)).labels, equals([]))
```

`t.context.github.requests` lists every request the agent sent, with the person or bot behind its token and the status the emulator answered. Use it to check that a call ran as the right identity. Evals share the log, so find the request by the item the eval created:

```ts
const path = `/repos/acme/web/issues/${issue.number}/labels`
const labeling = t.context.github.requests.find(request => request.path === path)
t.check(labeling, equals({ method: 'POST', path, status: 403, actor: 'bob' }))
```

## 5. Test the GitHub channel

When the agent runs on [eve's GitHub channel](/integrations/eve#run-on-eves-github-channel) with credentials from Vercel Connect, wrap them in `underEmulation`:

```ts [agent/channels/github.ts]
import { connectGitHubCredentials } from '@vercel/connect/eve'
import { githubChannel } from '@github-tools/eve-extension/channels'
import { underEmulation } from '@github-tools/eve-extension/testing/agent'

export default githubChannel({
  credentials: underEmulation(connectGitHubCredentials('github/my-agent')),
  respondTo: 'writers',
})
```

Outside an emulated eval run, `underEmulation` returns its argument unchanged. In one, it replaces the webhook verifier and nothing else: Connect's verifier checks a Vercel OIDC signature that Connect adds when it forwards a webhook, and the emulator signs the way GitHub does, with the webhook secret. The channel still gets its token and its bot name from Connect's routes. A channel with no `credentials` needs no change, because it reads the variables `emulateGithub` sets.

`deliverWebhooksTo(t)` registers the agent's GitHub route as a webhook of every repository. From then on, a comment an eval creates reaches the agent, signed, and the eval builds no payload:

```ts [evals/mention.eval.ts]
import { defineEval } from 'eve/evals'
import { includes } from 'eve/evals/expect'
import type config from './evals.config'

export default defineEval<typeof config>({
  async test(t) {
    const { github } = t.context
    const web = github.repo('acme/web')
    await github.deliverWebhooksTo(t)

    const issue = await web.as('bob').createIssue({ title: 'Crash on save' })
    await web.as('alice').comment(issue.number, `@${github.app.slug} what does this repository do?`)

    const reply = await web.issue(issue.number).waitForComment({ by: 'app' })
    t.check(reply.body, includes('acme/web'))
  },
})
```

The turn runs after the webhook is answered, so the eval waits for the reply with `waitForComment` and doesn't read it right away. No identity mapping is needed on this channel: the commenter is the emulator user who posted the comment.

An approval on GitHub is a comment, and a reply that mentions the agent answers it:

```ts
const prompt = await web.issue(issue.number).waitForComment({ by: 'app' })
await web.as('alice').comment(issue.number, `@${github.app.slug} Approve`)
const result = await web.issue(issue.number).waitForComment({ by: 'app', after: prompt.id })
```

## 6. Test a sign-in

A person with `authorized: false` hasn't connected GitHub through Vercel Connect yet. Their first call asks them to sign in, and `completeSignIn` finishes the sign-in the way a browser does after they consent:

```ts [evals/evals.config.ts]
people: { alice: { role: 'write' }, carol: { role: 'write', authorized: false } },
```

```ts [evals/sign-in.eval.ts]
const asked = await t.send('Summarize acme/web', as('carol'))
t.check(asked.interactions.map(interaction => interaction.request.kind), equals(['sign-in']))

const resumed = await t.context.connect.completeSignIn(t, asked)
resumed.calledTool('github__getRepository')
```

`t.context.connect.revoke('alice')` invalidates the token Connect holds for alice at GitHub. Her next call gets `401`, eve drops the token it cached, and asks her to sign in again. `t.context.connect.requests` lists every token request with its subject and scopes, so an eval can assert the scopes an App token asked for.

## Where each check belongs

| Layer | Answers | Needs | Cost of a run |
| --- | --- | --- | --- |
| Wiring eval: [`mockModel`](https://eve.dev/docs/evals#deterministic-fixture-models) and the emulator | Do the tools register, do approvals prompt, does the channel answer? | A separate test agent, since the model is part of the agent | Seconds, no paid call |
| Behavior eval: your model and the emulator | Does the agent do the right thing for this request, as this person? | The agent as it ships | Model tokens |
| Shadow run: [`dryRun: true`](/approval#shadow-mode) on real repositories | Does it behave on real data? | A GitHub token | Model tokens and reads |

Tag evals by layer, such as `tags: ['wiring']`, and run the first on every push with `npx eve eval --tag wiring`. Run behavior evals on a schedule or a label, since they spend model tokens.

An emulator run doesn't replace a shadow run. An eval that passes shows the agent does the right thing against the emulator's model of GitHub. Before an agent gets write access to real repositories, run it with `dryRun: true` on them.

## What `t.context.github` has

| Member | What it does |
| --- | --- |
| `repo(name)` | A seeded repository, acting as its admin |
| `repo(name).as(person)` | The same repository, acting as a person |
| `createIssue({ title, body?, labels?, assignees? })` | Opens an issue |
| `createPullRequest({ title, body?, files?, base?, draft? })` | Opens a pull request from a new branch with the given files. The person needs Write |
| `comment(number, body)` | Comments in the conversation of an issue or a pull request |
| `createDiscussion({ title, body?, category? })` | Opens a discussion |
| `issue(number)`, `pull(number)` | `await` it for the current state. `.comments()` lists its comments, and `.waitForComment({ by, after?, timeoutMs? })` waits for one |
| `createRepo(owner)` | Creates a repository with a unique name, with every person's role |
| `octokit(person?)` | An Octokit bound to the emulator, for anything else |
| `deliverWebhooksTo(t)` | Sends the repositories' webhooks to the agent. Calling it again changes nothing |
| `requests`, `deliveries` | The requests the emulator answered, and the webhooks it delivered |
| `app.slug` | The agent's GitHub App. Its bot comments as `eve-agent[bot]` |

A repository can also be seeded with `private: true`, with `workflows: ['ci.yml']` so the workflow tools have a workflow to run, and with `alerts` for the security tools.

## What the emulators don't cover

- **The repository checkout.** eve's GitHub channel clones the repository into the sandbox with `git`, from `github.com`, and the redirect covers `fetch` only. The local sandbox skips the checkout and logs that it did.
- **`eve dev` and deployed targets.** The emulators start in an eval's `setup`, which only `eve eval` runs, and a deployment can't reach your machine. For a deployed target, use eve's [tool stubs](https://eve.dev/docs/evals/tool-stubs).
- **URLs.** `html_url` and other URLs in results name the emulator's host. Assert on numbers and state.
- **Other GraphQL.** The emulator answers the GraphQL documents the SDK sends. A tool of your own that sends another gets an error that says so.
- **Rulesets, running workflows, and auto-merge.** A branch has no ruleset rules. A workflow run starts and never finishes, and its job log is a placeholder. Auto-merge is recorded on the pull request and never merges it.
- **Organization roles and teams.** Roles come from `people`. A member of an organization is an admin of its repositories, which is how emulate models it.
- **Vercel Connect's webhook forwarding.** The emulator delivers webhooks straight to the agent, so Connect's check of a forwarded webhook isn't exercised.

The tools' GitHub client spaces writes at least one second apart, and three seconds for writes that notify people, such as an issue or a comment. It does the same in an eval, so an eval where the agent makes many writes takes that long.
