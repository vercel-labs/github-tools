To let an agent improve itself, connect it to the [Vercel MCP](https://vercel.com/docs/agent-resources/vercel-mcp) and give it a schedule: the Vercel MCP reads the agent's own [Agent Runs](https://vercel.com/docs/agent-resources/vercel-mcp/tools/agent-runs), with each run's status, token usage and trace, and the agent reports what was slow, what failed and what to change. This guide adds that loop to the [`examples/eve`](https://github.com/vercel-labs/github-tools/tree/main/examples/eve) agent, which already answers in Slack and on GitHub.

## What you'll build

Every Monday, the agent posts a review of its last week in a Slack channel: the slowest and most expensive runs, the failures, and up to three changes it proposes, each with the run IDs that show the problem. Reply in the thread with "open an issue for the second one" and it files the issue in its own repository, after you approve. Every morning, a second schedule checks the last day for failed runs and new runtime errors, and posts only when it finds one.

The agent never changes itself. It proposes, a person decides, and the change lands through a reviewed pull request like any other.

## Before you start

- The agent from [`examples/eve`](https://github.com/vercel-labs/github-tools/tree/main/examples/eve), deployed to Vercel with its Slack channel set up. Agent Runs are recorded for every eve agent deployed to Vercel, so a week of use gives the review something to read.
- The agent's code in a GitHub repository the agent's GitHub App is installed on, so it can file issues there.
- A Slack channel for the reports, with the Slack app invited. Keep it private: a trace contains what people asked the agent.

## 1. Create a Vercel connector

The Vercel MCP is an OAuth server. A schedule runs with no signed-in user, so the agent needs an app-scoped token that [Vercel Connect](https://vercel.com/docs/connect) issues on its own. From the agent's directory:

```bash [Terminal]
vercel connect create vercel --name github-agent
```

The CLI opens your browser to sign in to Vercel. Grant the team that owns the agent's project. The connector acts with your access, so you need access to that project. Attach the connector to the project:

```bash [Terminal]
vercel connect attach vercel/github-agent --yes
```

`vercel/github-agent` is the connector UID. `vercel connect list` shows it if you chose another name.

## 2. Add the connection

Each Vercel MCP tool takes a `teamId` and a `projectId`. Read both from `.vercel/project.json`, where `orgId` is the team ID, and add them to the project with the other settings the schedules use:

| Variable | Value |
| --- | --- |
| `AGENT_TEAM_ID` | `orgId` from `.vercel/project.json` |
| `AGENT_PROJECT_ID` | `projectId` from `.vercel/project.json` |
| `AGENT_REPOSITORY` | The agent's own repository, such as `my-org/github-agent` |
| `REVIEW_SLACK_CHANNEL` | The ID of the Slack channel for reports, such as `C0123ABC` |
| `MAINTAINERS` | Comma-separated eve principal IDs of the people who may ask follow-up questions, such as `slack:T0123:U0456` |

```bash [Terminal]
vercel env add AGENT_TEAM_ID production
```

Run `vercel env add` once per variable, then `vercel env pull` to copy them into `.env.local`.

The connection is one file. Its filename, `vercel`, prefixes every tool name, as in `vercel__list_agent_runs`:

```ts [agent/connections/vercel.ts]
import { connect } from '@vercel/connect/eve'
import { defineMcpClientConnection } from 'eve/connections'
import { isScheduleAuth } from 'eve/schedules'

const maintainers = new Set((process.env.MAINTAINERS ?? '').split(','))

export default defineMcpClientConnection({
  url: 'https://mcp.vercel.com',
  description: "This agent's own production activity on Vercel: Agent Runs with their traces, runtime errors and runtime logs. Read-only.",
  tools: {
    allow: ['list_agent_runs', 'get_agent_run', 'get_agent_run_trace', 'get_runtime_errors', 'get_runtime_logs'],
  },
  toolCall: {
    providedArguments: {
      teamId: () => process.env.AGENT_TEAM_ID!,
      projectId: () => process.env.AGENT_PROJECT_ID!,
    },
  },
  auth: ({ session }) => {
    const caller = session.auth.current
    if (isScheduleAuth(caller) || (caller !== null && maintainers.has(caller.principalId))) {
      return connect({ connector: 'vercel/github-agent', principalType: 'app' })
    }
    return {
      principalType: 'app',
      getToken: () => Promise.reject(new Error('Only scheduled runs and maintainers can read this agent\'s runs.')),
    }
  },
})
```

Three settings keep the connection narrow:

- **`tools.allow`** lists five read-only tools. The Vercel MCP also deploys, edits environment variables and manages domains, and none of that is reachable here.
- **`providedArguments`** pins `teamId` and `projectId`. The model never sees either field, so it can only read this agent's project.
- **`auth`** issues a token only to a scheduled run or a maintainer. Anyone else who mentions the agent in Slack gets an error instead of the agent's runtime logs.

## 3. Write the review procedure

The schedule's message stays short and points at a skill. The skill holds the procedure, and the model loads it only when a review runs:

```md [agent/skills/self-review/SKILL.md]
---
description: Review your own production runs for slow, expensive and failed work, and propose changes to your instructions and config. Load this when a scheduled review fires or a maintainer asks for one.
---

# Self review

1. List the window's runs with `vercel__list_agent_runs` (`period: '7d'`, `pageSize: 100`), and the window before it with `from` and `to` for comparison.
2. Rank them three ways: failed or unanswered runs, the slowest, and the most tokens. Take the top three of each.
3. Read each of those traces with `vercel__get_agent_run_trace`. Look for:
   - a tool call that failed and was retried with the same input
   - the same tool called many times in one turn, such as paging through a list
   - a tool output much larger than the answer needed
   - a question to the person that your instructions already answer
   - a GitHub tool listed for the session and never called
4. Read `vercel__get_runtime_errors` for the window. Drill into a cluster with `vercel__get_runtime_logs`.
5. Turn what repeats into findings. A finding names the run IDs that show it, the cause, and one change in a named place: `agent/instructions.md`, an option in `agent/extensions/github.ts`, or a new skill. A pattern seen in one run is not a finding.

Reply with the week's numbers against the previous week, then at most three findings, the strongest first. Quote run IDs and tool names, never what a person wrote. End by asking which findings to file.

Open nothing on your own. When a maintainer asks you to file a finding, create one issue per finding in your own repository, with the evidence and the proposed change.

When nothing repeats, reply in one line that the week was clean.
```

The findings point at files the agent's own config already has, so each proposal is a change a person can review in a pull request.

## 4. Schedule the weekly review

A schedule with a `run` handler starts a session on a channel. This one opens a new Slack thread each Monday:

```ts [agent/schedules/weekly-review.ts]
import { defineSchedule } from 'eve/schedules'
import slack from '../channels/slack'

export default defineSchedule({
  cron: '0 8 * * 1',
  run({ to, waitUntil, appAuth }) {
    waitUntil(
      to(slack, { channelId: process.env.REVIEW_SLACK_CHANNEL! }).send(
        `Load the self-review skill and review your production runs from the last 7 days. Your source is in ${process.env.AGENT_REPOSITORY}.`,
        { auth: appAuth },
      ),
    )
  },
})
```

The session runs as the app, so `isScheduleAuth` lets the connection issue its token. The report lands in the thread, and the thread stays a conversation: a maintainer's reply continues the same session, with the traces it read still in context. Asking it to file a finding calls `createIssue`, which asks for approval in the thread before it runs.

On Vercel, schedules run in UTC, so `'0 8 * * 1'` fires at 08:00 UTC on Mondays.

## 5. Watch for failures every day

A weekly report is too slow for a failure. A second schedule checks the last day and stays quiet when there is nothing to say. It needs eve's `no_reply` tool, which ends a turn without posting:

```bash [Terminal]
npx eve add tool/no_reply
```

```ts [agent/schedules/failure-watch.ts]
import { defineSchedule } from 'eve/schedules'
import slack from '../channels/slack'

export default defineSchedule({
  cron: '0 7 * * *',
  run({ to, waitUntil, appAuth }) {
    waitUntil(
      to(slack, { channelId: process.env.REVIEW_SLACK_CHANNEL! }).send(
        'Check your production runs and runtime errors from the last 24 hours. If no run failed and no error cluster is new, call no_reply. Otherwise post one line per failure with the run ID and the likely cause.',
        { auth: appAuth },
      ),
    )
  },
})
```

This one needs no skill: it reads two lists and posts a few lines.

## Run it

`npx eve dev` never fires schedules on their own, so it serves a route that fires one by name:

```bash [Terminal]
npx eve dev
```

```bash [Terminal]
curl -X POST http://localhost:2000/eve/v1/dev/schedules/weekly-review
```

The review reads the deployed agent's production runs, and the report appears in the Slack channel. Reply "file the first finding" in the thread and approve the issue. When the report reads well, deploy with `npx eve deploy`, then check **Settings → Cron Jobs** in the Vercel project for both schedules.

## FAQ

::accordion

:::accordion-item{label="Can the agent change its own instructions?"}
Yes, through a pull request. Ask in the thread, for example "open a pull request with that change to `agent/instructions.md`". The GitHub tools create the branch, the commit and the pull request, and each write asks for approval. The agent can't merge it unless you approve that too, and it takes effect on the next deploy. Keep the merge with a person: an agent that rewrites its own prompt without review drifts in ways no single change shows.
:::

:::accordion-item{label="What if I don't want the agent to read conversations?"}
Remove `get_agent_run_trace` from `tools.allow`. The review then works from run metadata alone: status, duration, model, trigger and token usage, which still finds slow and failing runs but not why they happened. A trace holds what people asked the agent, including Slack messages and GitHub content.
:::

:::accordion-item{label="Does the review cover cost?"}
Agent Runs report tokens, not dollars. For spend per model, read the [AI Gateway](https://vercel.com/docs/ai-gateway) usage for the project, or price the token counts from the gateway's model list.
:::

:::accordion-item{label="Why not a markdown schedule?"}
A markdown schedule has no channel. It discards the reply, and a tool that needs approval fails the session instead of waiting. The handler form posts to Slack, so the report is readable, and filing an issue can wait for your answer.
:::
